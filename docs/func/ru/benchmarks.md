# Производительность

Методика и эталонные результаты нагрузочных тестов. Воспроизведение —
инструментами [`bench/`](../../bench/README.md); перед применением цифр
к другому железу прочитать раздел «Ограничения методики».

## Окружение эталонного прогона

Прогон 2026-09-11 на живом homelab-инстансе (не изолированный стенд —
см. оговорки ниже).

| Параметр | Значение |
|---|---|
| Версия Хражевника | v1.0.0 (`git.yadr00.internal/alexrus1234/khrazhevnik:latest`) |
| Конфигурация | S3 + PostgreSQL: RustFS и postgres — bare-metal systemd-сервисы NAS (4 vCPU), связь по выделенному P2P-линку |
| Хост контейнера | ВМ panelka: 4 vCPU / 8 GB RAM, rootless podman (quadlet), сосед — NORA на той же ВМ |
| Нагрузчик | k6 v2.2.0, отдельная Windows-машина в LAN |
| Сеть нагрузчик↔инстанс | ~2.5 Gb/s (пиковая отдача 295 MB/s) |
| Remote | debian (apt, proxy); объекты: 4 метаданных 140 KB–13.3 MB + 10 пакетов 53 KB–8.9 MB + ядро 107.7 MB |

## Сценарии

| # | Сценарий | Что измеряет |
|---|---|---|
| A | `hit-mixed` | тёплый кеш, смесь метаданных+пакетов: RPS-потолок, латентность, CPU/RAM |
| B | `stream-large` | пропускная способность отдачи одного крупного объекта (107.7 MB), VU = параллельные стримеры |
| C | `apt-storm` | шторм «apt update + install» (итерация ≈ 31 MB: 4 метаданных + 4 пакета), VU = клиенты |

Ступени — фиксированная интенсивность (constant-arrival-rate / VU) с
паузой 30 с между ступенями; каждая ступень — отдельный k6-сценарий,
коррелируемый с сэмплами контейнера и бэкендов по времени.

| r200 | 200 | 197 | 98.7% | 0.35 | 0.8 | 461 | 0.9 | 65 |
| r500 | 500 | 343 | 68.6% | 1.36 | 1.0 | 651 | 1.8 | 85 |
| r1000 | 1000 | 311 | 31.1% | 1.33 | 1.1 | 612 | 1.7 | 86 |
| r2000 | 2000 | 324 | 16.2% | 1.31 | 1.3 | 628 | 1.8 | 91 |

Агрегаты за прогон (730 с, 147k клиентских запросов, 141.5 GB отдачи,
~194 MB/s в среднем): клиент p50 92 мс / p95 6.4 с (p95 растёт на
ступенях ≥ r500 — время стрима больших объектов через насыщенный
тракт); сервер — **148 836 GET, все 200**, 128 MISS (ревалидация
индексов по TTL), 0 upstream-ошибок, 0 stale. «Ошибки» k6 (1.1–1.4% на
высоких ступенях) — сетевые обрывы на перегруженной трубе: сервер
ни одного 5xx не вернул.

Вывод: потолок доставки ~340 rps устанавливается не Хражевником —
насыщение read-path S3 (RustFS 85→91% CPU) и канала. До r200 включительно
— идеально чисто.

| v1 | 1 | 43.7 | 0.39 с | 6.5 с | 0 | 1.4 | 198 |
| v2 | 2 | 60.8 | 1.66 с | 8.9 с | 0 | 1.4 | 202 |

| v8 | 8 | 113.9 | 6.83 с | 13.6 с | 0 | 1.4 | 289 |

Одиночный стрим ходит рывками: медиана 0.39 с (≈276 MB/s, RustFS из

RustFS.

Вывод: пропускная способность упирается в S3-хранилище, не в инстанс;
контейнер при 8 параллельных 107MB-стримах — 1.4% CPU и 289 MB RSS.

## Узкие места

1. **Не бинарник и не каталог.** При ~340 rps и ~300 MB/s отдачи
   инстанс тратит ≤1.6% CPU и <1 GB RAM; каталог на PostgreSQL при
   сотнях тысяч SELECT — ≤1.8% CPU. Гипотеза «БД задохнётся первой»
   на таком профиле опровергнута.
2. **Узкое место — read-path S3-хранилища.** RustFS масштабирует
   отдачу сублинейно: 276 MB/s одиночный стрим → 114 MB/s на 8
   параллельных; CPU RustFS выходит на 90% при насыщении. Рост ёмкости
   — ядра/replication RustFS, не ресурсы Хражевника.
3. **Тракт ~2.4 Gbps** (пик 295 MB/s) — при исчерпании деградация
   ложится на клиентов (таймауты/обрывы у k6), сервер продолжает
   отдавать без единого 5xx (за все прогоны — 269 GB, ноль ошибок).

## Ограничения методики

- Живой инстанс: RustFS на NAS дёргался фоном (idle 25% CPU, всплески
  до 1.4 ядра — обслуживает и NORA); idle-baseline снят перед прогоном
  и вычтен качественно.
- Нагрузчик и инстанс в одном LAN (~2.5 Gb/s): измеренный потолок
  отдачи — потолок тракта, а не приложения; для оценки приложения
  смотреть CPU/RSS, а не MB/s.
- Пер-ступенчатая клиентская латентность снята для B и C (raw-json);
  для A — агрегат по прогону.
- fs+sqlite сместит узкое место с сети в локальный диск: порядок
  величин сохранится, цифры A/B переносимы только качественно.
