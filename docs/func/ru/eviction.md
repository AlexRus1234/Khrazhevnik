# Eviction кеша (авто-очистка старого кеша прокси)

Eviction — автоматическая очистка старых версий в кеше pull-through
прокси. Без неё immutable-объекты кеша хранятся вечно и кеш растёт до
размера носителя: пакеты одной и той же программы накапливаются
версиями, а свежая загрузка ничего не вытесняет.

Очистка удаляет только объекты кеша (`cache/<экосистема>/<remote-id>/…`).
Личные репозитории чистит
[ретеншн-политика](personal-repos.md), а не eviction — у них разные
политики, но общая таблица учёта обращений.

**По умолчанию eviction выключен.** Пока админ не включит политику,
ничего не удаляется (консервативный дебют: чистка удаляет объекты, а не
только читает).

## Что чистится

Проход идёт по одному remote и рассматривает версии внутри «семейства» —
группы объектов, которые являются версиями одного и того же пакета.
Семейство резолвит адаптер экосистемы по upstream-пути объекта:

| Экосистема | Семейство |
|---|---|
| apt | каталог исходника в пуле — `pool/main/h/htop/` |
| rpm-md, pacman, apk, xbps | префикс имени файла до версии-эпохи |

Объекты вне семейств — индексы, подписи, публичные ключи, служебные файлы
— проход не трогает: семейства резолвятся только для пакетов.

Версия удаляется при **двух условиях одновременно**:

1. у семейства **больше `min_versions` живых версий** (без этого проход не
   трогает семейство, где меньше либо равно минимуму версий);
2. к кандидату **не обращались дольше `max_age_days`**.

Версия считается живой, если выполнено **хотя бы одно** из условий — она
входит в топ-`min_versions` семейства по дате загрузки **ИЛИ** обращение к
ней свежее `now − max_age_days`. Защиты складываются по ИЛИ, поэтому
часто скачиваемая старая версия не удаляется, даже если она не в топе.

Упорядочивание версий — по дате загрузки (`ModTime`), не по разбору
номеров версий: важна свежесть, а не семантический порядок.

Давность обращения берётся из таблицы `object_access` (`scope=cache`):
кеш фиксирует обращения на выдаче **HIT/STALE**, MISS — нет. Если строки
обращений нет (объект загружен до включения учёта), давность считается от
даты загрузки. Запись обращений асинхронная и пачками, период —
`storage.access_flush_interval` (по умолчанию `30s`); только что
скачанный объект может ещё не иметь строки обращений — это нормально и
ошибки не даёт.

### MISS-самолечение

Если eviction удалил объект, к которому клиент обратится снова, прокси
для remote в режиме `proxy` отдаст прозрачный **MISS**: объект будет
скачан с upstream заново и снова закеширован. Это не ошибка и не 404 для
пользователя. Именно поэтому проход не разбирает индексы на ссылки: любое
повторное обращение само обновляет давность в `object_access`, а промах
самолечится перекачкой.

## Политика: per-remote и наследование

Политика задаётся отдельно для каждого источника (remote) и имеет
**три состояния** (`eviction` в теле remote, колонки
`remotes.eviction_min_versions` / `eviction_max_age_days`, миграция 0014):

| Состояние | Как задаётся | Смысл |
|---|---|---|
| наследовать | поле `null` в теле remote (или `NULL` в БД) | взять глобальный дефолт `[eviction]` из конфига |
| выключено | объект `{min_versions: 0, max_age_days: 0}` | для этого remote чистки нет |
| включено | объект с порогами | свои `min_versions` / `max_age_days` |

Разница между «наследовать» и «выключено» существенна: `NULL` в колонках —
это «не своё значение», `{0,0}` — «явно выключено для этого remote».
Поэтому колонки допускают `NULL`, а не `DEFAULT 0`.

Глобальный дефолт — секция `[eviction]` конфига (см.
[config.md](config.md)):

```toml
[eviction]
interval      = "24h"  # период суточного прохода; 0 — выключено
min_versions  = 0      # глобальный дефолт политики; 0 — eviction выключен
max_age_days  = 0      # 0 — без ограничения возраста
```

С `min_versions = 0` и `max_age_days = 0` (значения по умолчанию) политика
выключена. Сочетания полей валидируются доменом на старте: `min_versions=1`
с заданным возрастом (одна живая версия — окно 404: TTL-индексы в кеше
могут ссылаться на предыдущую версию) и `max_age_days` без `min_versions`
(удаление без гарантии минимума) отклоняются как ошибка конфига.

При `max_age_days = 0` при заданном `min_versions≥2` работает режим «только
keep-N»: удаляется всё сверх топ-`min_versions` независимо от обращений.

## Прогноз и применение

**Прогноз (dry-run)** ничего не удаляет — показывает, что политика
рассмотрела бы:

```sh
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:30202/api/v1/remotes/1/eviction/preview
```

Ответ — `candidates` (версии, прошедшие фильтр `min_versions`) и `totals`.
У кандидата `protected_by` — первая сработавшая защита: `""` — удаляется,
`access` — обращение свежее `max_age_days`. Версии, удержанные топ-N, в
список не попадают (их считает `totals.protected_by_min`). Пинов у кеша
нет: в прогнозе только `""` и `access`.

**Применение** запускает боевой проход фоновой задачей:

```sh
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:30202/api/v1/remotes/1/eviction/apply
# → 202 {"task_id": "..."}
```

Задача идёт с `kind=eviction`, label `remote-<id>`; наблюдать — `GET
/api/v1/tasks/{id}`. Повторный запуск при активной задаче того же remote —
409, лимит воркеров — 429, деградация без движка — 503. Полное описание
полей и кодов — в [api.md](api.md).

В [веб-админке](ui.md) политика, прогноз и применение собраны в блок
«Очистка кеша» в карточке источника.

### Триггеры

- **суточный проход** — по всем proxy-remote с включённой эффективной
  политикой; период `eviction.interval` (`24h`; `0` — выключено, тогда
  чистка только ручная). Проход последовательный, ошибка одного remote не
  останавливает остальных;
- **ручной прогноз** — `GET …/eviction/preview` (админ);
- **ручное применение** — `POST …/eviction/apply` (админ) или кнопка в GUI.

Триггер «сразу после скачивания» не используется: чистка в горячем пути
загрузки — лишний риск для выдачи, а давность всё равно важна только
вдолгую.

## Что НЕ чистится

- **Зеркала (`mode=mirror`).** Проход только по proxy-remote: зеркало —
  полная копия upstream, и churn «скачал → удалил → скачал» конфликтует с
  resume-diff sync. Зеркало чистит upstream, а не инстанс.
- **nix.** Хранилище content-addressed — старых версий одного пути не
  бывает, семейств нет. Адаптер nix не реализует резолвер семейств кеша,
  поэтому `preview`/`apply` для такого remote отвечают 400
  `eviction_unsupported` (честная ошибка, а не молчаливый no-op).
- **Прошлые версии mutable-объектов** (ключи вида `…-v<base36>`). Их чистит
  выметающая чистка хранилища (storagegc), eviction их только не трогает.
- **Marker `.retained`** by-hash-поколений apt — служебный объект
  генератора личного репо; с upstream он не приходит.
- **Объекты вне семейств** — индексы, подписи, ключи.
- **Личные репозитории** — их чистит ретеншн-политика
  ([personal-repos.md](personal-repos.md)).
- **Бюджет размера кеша (LRU/LFU при лимите размера)** — вне
  реализованного: критерий прохода только по числу версий и давности.

## Метрики

Проход экспортирует на `/metrics` (за auth, порт :30202):

- `khrazhevnik_eviction_runs_total` — число завершённых проходов по remote;
- `khrazhevnik_eviction_deleted_keys_total` — удалено объектов;
- `khrazhevnik_eviction_deleted_bytes_total` — освобождено байт;
- `khrazhevnik_eviction_failed_deletes_total` — сбоев удаления;
- `khrazhevnik_eviction_last_pass_timestamp` — время последнего прохода;
- `khrazhevnik_eviction_duration_seconds` — длительность одного прохода.
