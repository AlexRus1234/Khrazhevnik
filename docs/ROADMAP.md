# Дорожная карта (путеводитель)

Путеводитель: текущий статус, известные ограничения и направления
работ. Завершённые этапы — в [HISTORY.md](HISTORY.md); релизные
заметки уровня «что изменилось» — в корневом
[CHANGELOG.md](../CHANGELOG.md).

## Текущий статус

Код и документация выпущены по **v1.2.0** (2026-09-19): волна **XBPS**
(шестая экосистема, сессии 128–147) слита в main и выпущена — факты
формата и объём работ — в [HISTORY.md](HISTORY.md). Следующая волна —
«жизненный цикл объектов»: ретеншн личных репо → eviction кеш-прокси
(высокий приоритет, решение владельца 2026-09-19). Хвост: ручной
чеклист [RELEASE.md](RELEASE.md) §1–§3 по v1.2.0, включая отложенный
nix-smoke (M4-Р4 в [HISTORY.md](HISTORY.md)), — за владельцем, вне
релизной сессии 147. OCI-образ пушится в registry только с релизных
`v*`-тегов (сессия 103).

## Известные ограничения (решения планирования, не баги)

- История клиентских транзакций in-memory — рестарт очищает;
  счётчик кешированных пакетов не убывает — immutable-объекты не
  удаляются до eviction («Дашборд-v2»).

## Направления пост-v1

Приоритеты — решение владельца 2026-09-19: высокий — «жизненный цикл
объектов» (ретеншн личных репо → eviction кеш-прокси), средний —
уведомления, низкий — остальные функциональные направления, самый
низкий — расширение экосистем. Расширение экосистем и eviction
унаследованы из плана v1.0.0; остальные добавлены 2026-09-10 по
итогам v0.9.3.

- **высокий** — ретеншн-политики для личных репо → eviction
  кеш-прокси: одна волна «жизненный цикл объектов»; ретеншн первым
  (механика publish/reindex готова), eviction — следом (нужен резолв
  «семейства» пакета);
- **средний** — уведомления;
- **низкий** — автономный офлайн-экспорт зеркала; федерация
  инстансов (port.Ecosystem); предиктивный прогрев кеша (warm-up по
  зависимостям); OIDC/OAuth2; CLI (khzr-cli); глобальный поиск
  пакетов;
- **самый низкий** — расширение экосистем — pkg (FreeBSD/OpenBSD),
  Guix, Flatpak.

### Расширение экосистем

Направление — самый низкий приоритет, фокус на функциональных
направлениях (решение владельца 2026-09-19). Внутренний порядок на
случай запуска: сначала pkg — его модель «каталог + индекс» повторяет
уже решённые задачи; Guix — сразу за ним (протокол nix, переиспользует
nix-адаптер); Flatpak требует новой механики публикации и идёт
последним. Первой выполненной волной расширения стала XBPS (v1.2) —
факты формата и объём работ — в [HISTORY.md](HISTORY.md).

Каждая новая экосистема — адаптер `port.Ecosystem`: классификация
объектов (immutable/mutable), парсер метаданных, перечисление для
зеркала, генератор индексов личных репо — без изменений ядра и
контрактов. Критерий приёмки прежний: byte-exact прокси метаданных,
зеркало с resume, личные репо с подписью, фаззинг парсера, реальный
клиент в проверке.

#### pkg (FreeBSD, OpenBSD)

FreeBSD pkg(8): репозиторий — каталог с `meta.conf`, архивами
`packagesite.txz`/`digests.txz` (YAML-метаданные) и пакетами
`.pkg`/`.txz`. Индексы mutable, пакеты immutable; подпись репозитория —
RSA-ключ, публикуемый в конфиге клиента. Для личных репо — генератор
`packagesite`+`digests` и третий формат ключа (RSA) в signing-модуле.

OpenBSD pkg_add(7): общего индексного файла нет — метаданные каждого
пакета лежат внутри него самого, зависимости клиент разрешает сам;
репозиторий — просто каталог `packages/<arch>/`. Для кеш-прокси это
самый простой из возможных случаев: все объекты immutable,
отрицательное кеширование и singleflight работают вовсе без парсера;
зеркало — точная копия каталога.

Ограничение обоих: клиенты не Linux, CI-раннер (Linux-контейнеры) их
не покрывает — приёмочная проверка остаётся ручной по чеклисту
RELEASE.md; VM или отдельный раннер — открытый вопрос.

#### Guix

Бинарный кеш Guix говорит тем же протоколом substituter, что и nix:
narinfo + nar, content-addressed immutable-объекты. Прокси-случай
ложится на nix-адаптер почти без изменений; полное зеркало не
поддерживается по тем же причинам, что у nix (десятки ТБ), —
proxy-only. Специфика Guix, которую предстоит отработать: собственный
формат подписи narinfo (строка `Signature:` вместо nix-ового `Sig:`)
и свои клиентские ключи — отдельная ветка переподписи рядом с nix;
upstream — `ci.guix.gnu.org` / `bordeaux.guix.gnu.org`. Личные репо —
по модели nix: upload narinfo + nar с переподписью. Приёмка —
реальным клиентом `guix` (менеджер ставится поверх любого
дистрибутива).

#### Flatpak

Репозиторий Flatpak — хранилище OSTree: подписанный `summary`,
контент-адресованные объекты (sha256, zstd-упаковка), статические
дельты. Инвариант byte-exact выполняется естественным образом: объекты
immutable навсегда, `summary`/`summary.sig` — mutable с ревалидацией;
зеркало — рекурсивная HTTP-копия хранилища.

Личные репо — самая сложная из трёх задач, этап отложен отдельно:
публикация — это создание OSTree-коммитов (`flatpak build-export` +
`build-update-repo`), а не загрузка готовых артефактов; первым этапом
Flatpak ограничится прокси и зеркалом. Подпись — GPG, по формату
совпадает с OpenPGP-адаптером. Открытые вопросы: поведение клиентов при
неполном наборе дельт на зеркале, диапазонные запросы к pack-файлам,
целесообразность GC нессылаемых объектов.

### Автономный офлайн-экспорт зеркала

Выгрузка зеркала в автономный комплект для сети без доступа в
интернет (air gap): снапшот объектов + инструкция подключения
клиентов. Ключевая проблема — подписи: метаданные побайтовы и
корректны, но офлайн-клиенту нужно откуда-то доверять ключам.
Два кандидата, выбор не сделан:

- режим снапшота с отключением проверки на клиенте (`trusted=yes` в
  apt, `gpgcheck=0` в dnf, `SigLevel = Never` в pacman) — просто,
  но снимает защиту от подмены внутри доверённой сети;
- перенос экспорта в личное зеркало с переподписью ключом инстанса —
  переиспользует publish/reindex и механику переподписи, ключ уже
  раздаётся (`GET /repo/<name>/key.asc`), но экспорт перестаёт быть
  побайтовой копией upstream.

### Федерация инстансов (port.Ecosystem)

Каскадирование: upstream'ом remote'а становится другой Хражевник —
иерархии кешей и зеркал (региональный узел делегирует нагрузку
центральному). Точка расширения — адаптер `port.Ecosystem` поверх
существующих URL-префиксов, ядро не меняется. Открытые вопросы:
защита от циклов (A → B → A), прозрачность статистики и `X-Cache`
сквозь каскад, аутентификация между инстансами.

### Уведомления

Доставка событий инстанса: падение/восстановление sync, исчерпание
квоты, завершение больших задач (reindex, экспорт). Каналы-кандидаты:
webhook, email, индикатор в web-админке; событийная шина поверх
существующего реестра задач и аудита. Дизайн не фиксирован.

### Предиктивный прогрев кеша

Warm-up по зависимостям: после ревалидации индекса предсказывать
пакеты, которые запросят клиенты (новые версии + их дерево
зависимостей), и тянуть их фоном — первый запрос клиента уже HIT.
Опирается на парсеры метаданных экосистем; открытый вопрос —
приоритизация при ограниченной полосе и повторный прогрев на
частично скачанном индексе.

### OIDC/OAuth2

Внешняя аутентификация web-админки и API через identity-провайдер.
Локальный вход остаётся обязательным (bootstrap и break-glass-админ);
открытые вопросы — маппинг внешних identity на пользователей и роли
publish-RBAC, синхронизация token_version с внешними сессиями.

### Ретеншн-политики для личных репо

Авто-очистка старых версий в личных репо: keep-N поколений пакета
и/или TTL, с перегенерацией индексов и соблюдением by-hash retention.
Сейчас личное репо растёт неограниченно (в пределах квоты) — чистка
только вручную владельцем.

### Eviction кеш-прокси

Текущее поведение не меняется — immutable-пакеты хранятся навсегда.
Планы: удаление старых версий при кешировании новых (keep-N) и
LRU/LFU-политика при бюджете размера кеша.

Границы — чтобы будущая сессия не начинала ре-дизайн:

- proxy-режим only — зеркало хранит полную копию upstream, удаление
  конфликтует с resume-diff sync: churn «скачал → удалил → скачал»;
- keep N≥2 по умолчанию — TTL-индексы в кеше могут ссылаться на
  предыдущую версию, keep=1 даёт 404-окно;
- «семейство» пакета резолвит адаптер экосистемы: apt — pool-каталог
  `pool/main/h/htop/`; rpm-md/pacman/apk — префикс имени файла до
  версии-эпохи (эвристика — задел на проектирование, не решение);
- nix — исключение: content-addressed хранение, старых версий не
  бывает.

### CLI (khzr-cli)

Командный клиент поверх существующего REST API: логин и scoped-токены,
управление remotes и репозиториями, upload пакетов, статус задач —
для скриптов и CI, где curl+jq громоздок. Тонкий клиент без
дублирования бизнес-логики; контракт — тот же `/api/v1`.

### Глобальный поиск пакетов

Поиск по всем источникам инстанса — зеркалам, кешу и личным репо:
имя, версия, описание. Опирается на парсеры метаданных экосистем;
открытые вопросы — индексация в каталоге БД (объёмы уровня Debian) и
границы актуальности индекса.
